# 配車プランナー

車を出せる人と乗せてもらう人を、最寄り駅と乗車定員から自動で配車するWebアプリです。

## 作った理由

所属している大学のゴルフ部では、月1回のラウンドのたびに配車を決めています。部員は26人ほどで、そのうち車を出せるのは6人程度。毎回参加するメンバーが変わるので、誰がどの車に乗るかを毎回考え直す必要があります。

これが想像以上に大変でした。乗せてもらう側は運転手の最寄り駅まで電車で向かうことになりますが、住んでいる場所がバラバラなので「Aさんの車に乗るなら40分かかるけど、Bさんなら15分で着く」といった差が出ます。さらに車ごとに定員があるので、近い順に詰めていくと定員を超えてしまい、また考え直しになります。

早朝集合が多いので始発の有無も効いてきます。集合時刻に間に合わない人がいると、その人だけ別の車に移す必要が出てきて、そこからまた全体が崩れます。

この作業を毎回LINEでやりとりしながら決めていたので、自動化したいと思って作りました。部活に限らず、旅行やイベントなど複数人で車移動する場面なら使えるように設計しています。

## 機能

- メンバー登録（最寄り駅・車の有無・乗車定員）
- おでかけの作成（日付・目的地・参加メンバー）
- 運転手ごとの集合時刻設定
- 配車の自動最適化
- 各メンバーの出発時刻と所要時間の表示
- 始発に間に合わないメンバーの検出
- ユーザーごとのデータ管理

## 配車ロジック

1. 参加メンバーを運転手と同乗者に分ける
2. 同乗者それぞれについて、全運転手の最寄り駅までの所要時間をNAVITIME APIで取得
3. 合計の所要時間が一番短くなる組み合わせを整数計画で解く
4. このとき「車ごとの乗車人数の差は1人以内」という条件も同時に満たす

最初は、所要時間が短い順に上から詰めていく方法（貪欲法）で書いていました。動くには動くのですが、使っているうちに2つ問題が見えてきました。

ひとつは、合計時間が最短にならないことです。先に決まった人が席を埋めてしまうので、あとの人が遠い車に回されることがあります。

もうひとつは人数が偏ることです。駅のアクセスがいい運転手の車にみんなが集まってしまい、片方が満員なのにもう片方は1人、ということが起きました。

そこで整数計画に変えました。全員ぶんの組み合わせをまとめて評価して一番いいものを選ぶので、必ず最短になります。「人数の差は1人以内」のような条件も式として書けるため、偏りも同時に解決できました。

乗車定員は運転手を含む人数で登録します。4人乗りの車なら `4` と入力すると、同乗できるのは3人までになります。

## 工夫した点

**APIリクエストの節約**

無料枠が月500リクエストのため、駅名と駅IDの対応、および区間ごとの所要時間をDBに保存しています。同じ駅の組み合わせは2回目以降APIを呼ばないため、繰り返し使ってもリクエストをほとんど消費しません。集合時刻が未設定の場合は、計算しても結果が出ないのでAPIを一切呼ばないようにしています。

**API処理の分離**

API呼び出しは `navitime.py` に切り出しています。他の乗換案内APIに変更する場合も、このファイルだけ差し替えれば済むようにしました。

**API障害時に落ちない設計**

ステータスコードが200以外の場合や、経路が見つからない場合はNoneを返し、その組み合わせは選ばれないようにして処理を続行します。

**嘘の出発時刻を表示しない**

各運転手の集合時刻を到着時刻としてAPIに渡しているので、その時刻に間に合う電車の出発時刻が返ってきます。ただし間に合う電車がないと、前日まで遡った時刻が返ってくることがあります。そのまま出すと嘘の案内になるため、前日の時刻・始発前の時刻・集合より2時間以上早く着いてしまう便は「間に合う経路なし」として画面に出さないようにしました。

- ログインとユーザー登録、ユーザーごとのデータ分離
- NAVITIME APIの呼び出しと、駅ID・所要時間のDBキャッシュ

- 画面のHTMLとCSS
- RenderとPostgreSQLでのデプロイ

アプリの土台と、APIを使って実際に配車を出すところまでは自分で作っています。

### Claude Codeを使った部分
